# X.bot 包装素材

把现有 X.bot 运行时视为唯一实现入口。复用仓库中的监听器、包装服务、Eagle 索引和 SQLite 状态机，不另建平行机器人或临时检索脚本。

## 开始工作

1. 定位包含 `bot/lib/packaging-service.js` 的项目根目录。已在该仓库中时直接使用当前目录。
2. 读取根目录 `AGENTS.md`，再按其中顺序读取 `docs/CONTEXT.md`、`README.md`、`docs/STATUS.md` 和 `docs/WORKFLOW.md`。
3. 检查当前分支、`git status --short --branch` 和最近提交。保留用户已有修改，不重置、不覆盖无关文件。
4. 涉及消息流程、安全边界、数据关系或交付规则时，读取 `docs/DECISIONS.md` 的有效决策及核心项目文档对应章节。
5. 读取 [behavior-contract.md](references/behavior-contract.md) 掌握不可破坏的业务契约；需要定位实现、命令或测试时再读取 [repo-map.md](references/repo-map.md)。

若参考文件与仓库文档或代码不一致，记录差异并以用户当前要求、有效决策、当前状态和真实行为的优先级处理，不静默选择。

## 判断任务类型

- 用户要解释、盘点或报告状态：只读检查当前文档、代码、Git 和必要的运行状态，给出证据，不修改实现。
- 用户要诊断：查事件状态、进程、日志、索引和测试，定位根因；除非用户要求修复，否则不改代码、不重启服务。
- 用户要修改、接入或“支持一种新消息/行为”：直接扩展现有监听器和 `PackagingService`，补最小回归测试，并同步项目文档。
- 用户要启动、恢复或验证 bot：使用现有启动脚本和规范运行根目录，验证进程、事件消费者、就绪日志与包装目录加载，不只看计划任务状态。
- 用户要检索或发送真实包装：保持飞书端的候选确认闸门，不从 Codex 侧绕过原查询人确认直接发送源文件。

## 实施包装查询行为

保持以下主链：

1. 要求新的包装查询明确 `@X.bot`，私聊和群聊一致。
2. 规范化 `text` 与带文字的 `post` 后，按项目正式名称或别名优先识别，再结合包装类型、标签和自然语言意图检索。
3. 未知项目返回当前可查项目列表和查询示例，不创建待确认记录。
4. 最多返回 3 个候选，把编号、名称、说明和 PNG 合并成一条可回复的飞书富文本消息。
5. 只通过该候选消息的 `reply_to` 定位查询。无回复引用时不得读取最近一条待确认记录、继承项目或发送源文件。
6. 只允许原查询人确认；支持编号、确认、拒绝和回复候选后的类型追问。候选默认 20 分钟过期，多条查询可独立并存。
7. 确认后发送配对 ZIP，并把结果回复到最初查询消息下。大文件使用现有飞书云盘降级；SQLite 状态和飞书幂等键共同防重复。
8. 仅图片背景只发送 PNG 并明确没有工程 ZIP，不创建源文件确认流程。

纯图片消息不得触发视觉检索，也不得下载或发送到外部视觉模型。私聊可解释当前不具备识图能力；群聊仅在有效 `@X.bot` 或回复 X.bot 时回应，保持低噪音。

## 维护索引与入库联动

- 让 Eagle 保存素材，让 SQLite 保存项目、包装、版本、预览、源文件和查询/交付状态的稳定映射；不得依赖同名文件建立唯一关系。
- 只通过 Eagle Plugin API 或 Web API 修改 Eagle 数据。bot 的库目录同步只能只读解析 `.library`，不得直接写内部 `metadata.json`。
- 继续由插件写入 `packaging-ingest-events.jsonl`，由 bot 消费者按 `event_id` 幂等写 SQLite 并强制刷新索引。失败事件必须保留重试能力。
- 源文件统一为含 AEP 与依赖的 ZIP，不发送裸 `.aep`。不得把 `.library`、AEP、ZIP、运行数据库、日志、密钥或 Token 提交到 Git。
- 多终端中央索引服务仍是暂缓项；除非用户明确重启该范围，不把单机链路冒充为已完成的共享部署。

## 修改代码

1. 先从消息入口追踪到 `tryHandleConfirmation`、`tryHandleQuery`、`startQueryFromResult` 和交付方法，确认改变落在哪个状态转换。
2. 保持路由优先级：明确新查询优先；有 `reply_to` 的候选操作其次；无引用消息走新查询或普通聊天。
3. 把意图识别和排序放在 `package-intent.js`，把候选/确认/发送状态放在 `packaging-service.js`，把飞书事件规范化与 transport 放在监听器，避免重复业务规则。
4. 为新增行为只补关键边界和已知回归风险测试。优先修改对应的三个包装测试文件，再按影响范围扩大验证。
5. 改变消息、确认、源文件权限、图片外发、Eagle/SQLite 边界时，更新有效决策和核心项目文档；一般实现变化至少更新 `docs/STATUS.md` 与 `CHANGELOG.md`。
6. 核心项目文档变化先改仓库主版本，再同步外部工作副本并比较内容或哈希。

## 验证与交付

按改动风险选择最小充分验证：

- 意图或排序：运行 `package-intent` 测试。
- 候选、确认、发送：运行 `packaging-service` 测试。
- 消息类型、@ 门控或路由：运行监听器测试。
- 索引或入库事件：运行 `eagle-sync`、数据库与 `ingest-sync` 测试。
- 跨模块变化：运行 `npm run check` 和 `npm test`。
- 真实运行恢复：再验证事件总线、唯一监听器、日志中的 AI 配置、包装目录同步和 `ready` 行。

完成前运行 `git diff --check`，检查没有密钥和运行资产，报告分支、验证结果、未完成事项以及任何预先存在的工作区修改。除非用户要求，不提交、不推送。
