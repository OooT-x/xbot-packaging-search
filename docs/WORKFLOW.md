# 开发与版本管理流程

## 单一迭代流程

每次需求、修复或实验都按以下顺序进行：

1. 读取 `STATUS`、核心文档和相关决策。
2. 检查 Git 工作区和现有用户修改。
3. 明确本次目标、范围外事项和验收方式。
4. 创建 `codex/<topic>` 工作分支。
5. 小步实施并执行对应验证。
6. 更新状态页、变更日志及必要的决策记录。
7. 创建一个或多个主题清晰的提交。
8. 报告完成内容、验证证据、提交和遗留事项。

测试策略：测试集以风险覆盖为目标，优先保留能证明新增行为、关键边界和历史回归的最小用例集合；不重复覆盖没有变化的路径，也不以测试数量作为完成指标。

## 分支规则

- `main`：配置远程仓库后作为稳定分支，只接收已验证的里程碑或修复。
- `codex/<topic>`：功能、文档、重构和实验分支。
- 一个分支只承担一个主题；主题改变时新建分支。
- 不对含有用户未提交工作的分支执行破坏性重置。

## 提交规则

提交信息使用以下前缀：

- `feat:` 新能力
- `fix:` 缺陷修复
- `docs:` 文档或项目管理
- `refactor:` 不改变外部行为的结构调整
- `test:` 测试
- `chore:` 构建、依赖和维护

每个提交应满足：

- 只有一个可解释的逻辑目的。
- 不混入无关格式化或用户修改。
- 提交前通过 `git diff --check` 和本次范围对应的验证。
- 不包含密钥、运行数据或生产素材。

## 版本规则

项目存在两个独立版本号：

- **核心文档版本**：例如 `v1.1`，只表示需求和技术方案版本。
- **软件版本**：采用语义化版本 `MAJOR.MINOR.PATCH`，由 Git 标签 `vX.Y.Z` 表示。

软件版本含义：

- `MAJOR`：不兼容的数据模型、接口或使用流程变化。
- `MINOR`：向后兼容的新功能或新阶段交付。
- `PATCH`：向后兼容的缺陷修复和小调整。

在出现首个可运行闭环前不创建正式软件发布标签。

## 需求反复和实验管理

- 不通过删除历史掩盖方向变化。
- 被替代的方案保留在 `DECISIONS` 中，并标记“已取代”。
- 实验性功能先标记“试行”，明确成功条件和回退方式。
- 数据库变化必须使用迁移，不手工覆盖生产数据库。
- 改变飞书消息行为、文件发送权限或外部 AI 数据流向时，必须单独记录决策。

## 交付检查清单

- [ ] 本次范围与核心文档一致。
- [ ] 测试或真实接口验证已完成。
- [ ] `STATUS.md` 已更新。
- [ ] `CHANGELOG.md` 已更新。
- [ ] 架构/产品规则变化已写入 `DECISIONS.md`。
- [ ] 核心文档及外部副本需要时已同步。
- [ ] Git 工作区干净。
- [ ] 分支、提交、验证结果和遗留事项已报告。
