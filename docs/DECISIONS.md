# 项目决策记录

本文件记录会影响多个模块或长期行为的决策。需求发生反复时，不删除旧记录；把旧决策状态改为“已取代”，并新增替代决策。

## 状态定义

- **有效**：当前必须遵循。
- **试行**：正在验证，可在复盘后调整。
- **已取代**：保留历史原因，但不再执行。
- **废弃**：确认不采用。

## D-001：项目名优先检索

- 日期：2026-08-18
- 状态：有效
- 决策：检索优先级以项目名称精确匹配和项目别名匹配为先，图片相似度只作为辅助召回方式。
- 原因：同一包装可能被多个项目复用，发送人通常记得项目名，但不一定知道准确包装名称。

## D-002：预览后确认再发送源文件

- 日期：2026-08-18
- 状态：有效
- 决策：机器人先返回 PNG 候选，只有原查询人回复候选消息确认后才发送 ZIP。
- 原因：降低模糊匹配、版本并存和群聊误确认导致的误发风险。

## D-003：Eagle 存素材，SQLite 存稳定映射

- 日期：2026-08-18
- 状态：有效
- 决策：Eagle 保存预览图和源文件；SQLite 保存项目、包装、版本、Eagle ID、源路径和 AE 合成名称之间的关系。
- 原因：文件名、位置和同名关系可能变化，不能作为唯一关联依据。

## D-004：源文件统一使用 ZIP

- 日期：2026-08-18
- 状态：有效
- 决策：发送包含 AE 工程及依赖素材的 ZIP，不发送裸 `.aep`。
- 原因：避免工程打开后缺少外部依赖。

## D-005：新查询必须明确提及机器人

- 日期：2026-08-18
- 状态：有效
- 决策：私聊和群聊中的新包装查询都必须明确 `@X.bot`；进入候选确认阶段后，原查询人回复时不需要再次提及。
- 原因：降低机器人噪音和群聊误触发。

## D-006：待入库目录按项目组织

- 日期：2026-08-19
- 状态：有效
- 决策：`00_待入库` 下每个项目建立一个文件夹，项目文件夹内同时放置该项目的 PNG 预览和 ZIP 源文件。
- 原因：项目是第一检索入口，同项目素材集中处理更符合实际入库习惯。

## D-007：Eagle 入库助手放到第五阶段

- 日期：2026-08-19
- 状态：有效
- 决策：Eagle 入库助手采用窗口插件形态，在第五阶段实现；插件负责入库和索引同步，不替代 X.bot 飞书服务。
- 原因：先完成文字检索闭环，再用已稳定的数据规则固化插件，减少过早自动化带来的返工。

## D-008：Git 中的核心文档为主版本

- 日期：2026-08-19
- 状态：有效
- 决策：`docs/飞书机器人包装素材检索项目文档.md` 为受版本控制的主版本，外部同名文档作为工作副本同步维护。
- 原因：长期项目需要可追溯的变更历史，同时保留用户原有文档使用位置。

## D-009：Eagle 数据只能通过官方 API 修改

- 日期：2026-08-19
- 状态：有效
- 决策：使用 Eagle Plugin API 或 Web API 修改目录、标签和素材，不直接编辑 `.library` 内部元数据文件。
- 原因：避免破坏资源库内部一致性，并保留清晰的操作边界。

## D-010：AE 包装提取是 Eagle 入库的前置环节

- 日期：2026-08-19
- 状态：有效
- 决策：第五阶段增加 AE 包装提取辅助工具。用户在 AE 中明确选择可复用合成后，工具在工程副本或收集副本上生成静态 PNG 预览、包含依赖的 ZIP、AE 收集报告和标准化 manifest，再交给 Eagle 入库助手审核。工具不得直接精简、改名或覆盖原工程。
- 原因：真实项目工程同时包含包装合成、业务画面、示例素材、字体和第三方效果。直接把项目目录导入 Eagle 会产生重复文件和错误映射；先在 AE 侧按合成提取和校验，才能得到可复用、可追溯的入库单元。

## D-011：本地项目文件夹对应一个待入库批次

- 日期：2026-08-19
- 状态：有效
- 决策：用户拖入或选择一个本地项目包装文件夹时，Eagle 入库助手在 `00_待入库` 下创建一个对应的批次文件夹。插件递归扫描源目录，但优先按 manifest 明确列出的路径导入；没有 manifest 时只识别符合待入库规则的预览 PNG 和源文件 ZIP。展开的 `.aep`、业务视频、截图、依赖图片和 Report 只用于校验，不原样镜像到 Eagle。每次导入生成稳定的 `batch_id`，重复导入必须提示复用、更新或新建批次，不能静默产生重复素材。
- 原因：按文件夹保留项目上下文更符合制作人员的交付习惯，但原样递归导入会把收集工程的展开目录、业务素材和 ZIP 同时导入，造成重复、噪声和误发风险。

## D-012：Eagle 入库不复核已打包 ZIP 内依赖的必要性

- 日期：2026-08-19
- 状态：有效
- 决策：依赖素材是否需要进入 ZIP，由上游 AE 包装提取和打包环节负责。对于已经打包完成的 ZIP，Eagle 入库环节只校验文件存在、可读取、格式正确，并能与唯一的 PNG 和包装记录配对；不在此环节解包或逐项判断 ZIP 内视频、截图、图片等依赖是否必要。字体和第三方效果继续作为依赖事实和警告记录。
- 原因：重复判断 ZIP 内部素材会把上游提取职责带入 Eagle 审核，既增加人工成本，也可能误删合成真实依赖。入库环节应专注于分类、配对、元数据和可追溯性。

## D-013：正式素材描述只记录事实字段

- 日期：2026-08-19
- 状态：有效
- 决策：Eagle 正式素材描述记录项目、原 AE 项目、`package_id`、包装名称、类型、版本、AE 合成、`batch_id`、配对 Eagle ID、状态、字体和第三方效果等稳定事实。用户确认、审核过程、ZIP 校验边界和操作历史不写入素材描述。
- 原因：描述用于日常检索和追溯，混入一次性流程话术会制造噪声，并让同一包装的 PNG 与 ZIP 元数据难以长期保持一致。

## D-014：正式入库后允许清理空批次文件夹

- 日期：2026-08-19
- 状态：有效
- 决策：正式素材已从待入库批次移入分类目录后，可以删除空的批次文件夹及空子目录。删除前必须递归确认目标文件夹直接素材数、后代素材数和所有子目录内容均为空；任何一级不为空都必须终止。当前官方 Web API 和 Folder Plugin API 不提供删除方法时，保留空文件夹并由用户在 Eagle 界面手动删除，不得直接修改资源库元数据。
- 原因：清理空批次可以避免 `00_待入库` 长期积累无效目录，同时递归空目录检查和官方接口边界能防止误删仍有素材的批次。

## D-015：复用既有 X.bot 监听器并将包装检索作为独立模块接入

- 日期：2026-08-19
- 状态：有效
- 决策：既有 X.bot 的 Node 事件监听、群聊 `@mention` 门控、大模型、周报和语音能力继续保留；代码主版本迁入本仓库，包装检索以独立的 Eagle 同步、SQLite、意图解析和确认状态模块接入同一事件消费者。运行时可通过 `LARK_BOT_RUNTIME_ROOT` 继续复用原飞书目录中的回复规则、语音资源和日志，避免同时启动第二个事件消费者。由于 `lark-cli event consume` 的 compact 消息事件不含回复关系，确认阶段使用 bot 身份读取当前消息详情中的 `reply_to`，再校验原查询人和候选消息。Eagle 数据只通过官方 API 读取元数据；原文件路径依据官方返回的当前库路径和稳定 Eagle item ID 只读解析并写入 SQLite，不修改 `.library` 内部文件。
- 原因：新建独立消费者会造成重复收消息和回复，重写既有机器人又会破坏已经验证的能力。模块化接入能保留现有行为，并让未来 Eagle 插件提供 `filePath` 时只替换同步适配层。

## D-016：索引同步可只读解析指定 Eagle 库目录

- 日期：2026-08-19
- 状态：有效
- 决策：包装索引同步支持直接只读解析指定 Eagle 库目录（库根 `metadata.json` 与 `images/*.info/metadata.json`），通过 `LARK_BOT_EAGLE_LIBRARY_PATH` 指定，默认 `E:\Eagle资源库\包装.library`。该模式不依赖 Eagle 当前活动库，也不修改 `.library` 内部任何数据；Eagle 界面可继续停留在其他库。
- 原因：Eagle Web API 只能访问当前活动库，而用户需要在保留当前 Eagle 界面库的同时让 bot 检索包装库。

## D-017：超限源文件走飞书云盘链接降级

- 日期：2026-08-19
- 状态：有效
- 决策：超过飞书即时消息单文件上限（约 30MB，bot 上传接口拒绝）的源文件，确认后由 bot 上传到自身飞书云盘根目录，并在原查询消息下回复下载链接；不拆分、不压缩源文件。小文件仍直接发送。
- 原因：机器人上传接口对单文件大小限制远小于用户通道；实测 61.7MB ZIP 上传云盘成功且链接可下载。

## D-018：多条候选查询并存，语境延续不取消旧查询

- 日期：2026-08-19
- 状态：有效
- 决策：新查询和语境延续（如“看看背景”）都不取消已存在的待确认查询；多条查询并存，各自保留 20 分钟，回复任一旧预览仍可确认对应候选（候选级幂等保证已发送的不重复发送）。只有 20 分钟过期或用户明确拒绝（“不是/都不对”）才使查询失效。
- 原因：用户会在已看到的候选基础上继续换类型查看，旧预览突然失效会导致“已发送或待确认候选无法再回复”的体验问题。

## D-019：包装查询触发采用规则快路径 + 大模型语义兜底

- 日期：2026-08-19
- 状态：有效
- 决策：包装查询触发分为两层：规则层要求项目名（或别名）命中且带动作词或领域词其一；规则未命中但消息已 `@X.bot` 时，由大模型判断是否为包装查询并提取项目与类型。`@X.bot` 门控在群聊与私聊均保留；AI 不可用或判断失败时自动回退规则，不拦截普通聊天。
- 原因：纯关键词规则无法覆盖自然说法，而完全放开触发会造成群聊误触发；双层判断在灵活性与低噪音之间取得平衡。

## D-020：入库助手插件采用“窗口插件 + 纯逻辑扫描引擎 + Eagle API 导入层”

- 日期：2026-08-20
- 状态：有效
- 决策：Eagle 入库助手插件拆为三部分：`eagle-plugin/lib/scan.js` 提供可单测的扫描/配对/四状态/批次逻辑；`eagle-plugin/lib/eagle-api.js` 负责 Eagle Plugin API 适配与导入；`index.html`/`js/plugin.js` 只做窗口交互。导入先落到 `00_待入库/<项目>包装` 批次文件夹，按 D-013 写事实字段描述并在 PNG/ZIP 中回写配对 Eagle ID。正式分类目录归位、SQLite 索引写入和重复导入三选项（复用/更新/新建）作为下一增量；扫描结果中的 `batchKey`（文件相对路径 + 大小哈希）用于后续重复导入检测。
- 原因：把扫描、配对与批次规则固化成纯模块，可以先用自动化测试验证规则，再接入真实 Eagle 环境；一次性实现正式归位和索引同步会引入较多耦合，不利于回滚。

## D-021：导入与入库分离为两个独立操作

- 日期：2026-08-20
- 状态：有效
- 决策：插件提供两个独立按钮。`导入` 只负责把本地项目包装文件夹扫描并导入 `00_待入库/<项目>包装` 批次；`入库` 读取用户选择的待入库批次，按 5.7 正式入库规则把 PNG 归位到 `01_预览图/<类型>`、ZIP 归位到 `02_AE源文件/<类型>`，把标签中的 `00_待入库` 替换为对应正式目录，并在移动前完成 PNG+ZIP 配对校验（缺配对、缺类型、未知类型或重复记录均阻止入库）。入库完成后批次为空时提示用户在 Eagle 界面手动删除空批次文件夹。D-020 中“正式分类目录归位作为下一增量”的表述由本决策取代；SQLite 索引写入和重复导入三选项仍是后续增量。
- 原因：导入与正式入库是两个独立审核节点。分开执行可以让素材先在待入库批次中统一检查、修正，再一次性归位，避免“导入即归位”让错误素材直接进入正式目录。

## D-022：正式入库不依赖插件导入

- 日期：2026-08-20
- 状态：有效
- 决策：`导入` 仅作为“外部本地文件夹 → Eagle 待入库批次”的可选搬运和预检工具。`入库` 必须独立读取 `00_待入库` 下用户选择的项目批次，并递归覆盖其子目录；素材即使由用户直接使用 Eagle 文件夹导入、没有插件注释，也要按受控位置、文件名和目录名重新识别 PNG/ZIP、建立候选配对，并允许在预检界面补充缺失的包装类型。只有唯一配对且字段完整的记录才能正式归位；归位时再通过 Eagle Plugin API 写入稳定 ID、配对关系、标签、事实描述和规范名称。
- 原因：待入库目录是正式入库的事实来源，素材进入该目录的方式不应决定后续是否可处理。让入库依赖插件导入生成的注释，会使 Eagle 自带文件夹导入和人工整理的批次无法使用，也混淆了两个按钮的职责边界。

## D-023：标注与人名条默认归入信息条

- 日期：2026-08-20
- 状态：有效
- 决策：Eagle 入库助手在本地文件扫描、手动导入批次扫描和 manifest 解析中统一使用包装类型别名规则。包装名称、文件名、目录名、标签或 manifest 类型包含“标注”或“人名条”时，默认把包装类型规范化为“信息条”；预检界面仍允许用户手动改正。
- 原因：项目分类规则已经把人名条和标注条统一纳入信息条。自动入库应直接执行该规则，避免“小标注”等明确素材反复停在待补充状态。

## D-024：明确的新包装查询优先于历史候选确认

- 日期：2026-08-20
- 状态：有效
- 决策：消息明确 `@X.bot`，并命中已知项目名（或别名）及包装动作词/领域词时，优先按新包装查询处理，不得先关联当前会话的历史待确认记录。候选确认优先依赖飞书 `reply_to`；没有回复引用时，只有纯确认话术或不含项目名的类型追问可以回退最近待确认查询。历史候选过期只影响该候选的确认，不得截断可独立成立的新查询。该决策补充 D-005、D-015、D-018 和 D-019，不改变多查询并存与 20 分钟有效期规则。
- 原因：确认回退本来用于补偿 compact 消息事件缺少回复关系。如果领域词（如“背景”）本身就能触发回退，明确的新查询会被错误绑定到旧候选，并因旧记录过期而提前结束。先识别可独立成立的新查询，可以保留无引用确认能力，同时避免历史状态污染新的检索意图。

## D-025：AE 包装整理采用 ScriptUI 面板与原生 Collect Files 半自动闭环

- 日期：2026-08-20
- 状态：已取代（由 D-026 取代）
- 决策：AE 包装整理第一版采用可停靠的 ExtendScript/ScriptUI 面板。面板读取用户在 Project 面板中明确选择的包装合成，负责逐条元数据、代表帧 PNG、工程静态风险扫描、标准化 manifest、收集目录 ZIP 压缩和交付检查；依赖收集仍打开 AE 原生 `File > Dependencies > Collect Files` 对话框并由用户确认 `For Selected Comps`、输出位置和 Report。第一版默认不自动执行 `Reduce Project`，不修改、改名、删除或覆盖原工程中的项目项。缺失素材、跨合成引用和扫描失败阻止入库；字体与疑似第三方效果作为人工复核警告。
- 原因：After Effects 的 Collect Files 已能可靠生成工程副本、依赖和 Report，而 Reduce Project 会删除非从属合成，跨合成表达式还可能被一并移除。把高风险动作保留在 AE 原生可见流程中，同时自动化重复的元数据、预览、打包和配对工作，能先建立可回滚的真实闭环，再根据项目样本决定是否增加更深自动化。

## D-026：AEP 收集主入口改为外部合成浏览与收集工具

- 日期：2026-08-20
- 状态：试行
- 决策：AE 包装收集主入口改为 Windows 外部工具。工具使用 MIT 许可的公开 `py-aep` 直接读取 AEP，必须在不启动 After Effects 的情况下显示工程内全部合成、父级使用关系和内部预合成；用户明确选择合成后，工具递归保留嵌套合成和图层素材，只在新目录写出精简 AEP、素材目录和 manifest，并在交付前重新解析输出 AEP。BHY Collect Pro 仅作为产品行为参考；由于随包没有源码或许可证，不修改、不复制、不重新分发其 EXE，也不把其私有缓存格式作为稳定接口。旧 ScriptUI 面板保留为历史和代表帧 PNG/AE 内验证能力，不再作为收集主入口。
- 原因：用户需要在不打开 AE 的情况下直接浏览并选择工程内合成，且第三方 BHY 在真实工程中出现“后台识别到 11 个合成、界面缓存却为空”的同步问题。基于公开依赖重做可以把“合成必须完整显示”和“收集结果必须自检”固化为可测试能力，同时维持不覆盖原工程、跨合成表达式需人工复核的安全边界。

## D-027：每个合成收集后生成独立 ZIP

- 日期：2026-08-20
- 状态：有效
- 决策：外部 AEP 收集工具对每个用户选中的合成分别生成一个展开收集目录和一个同名 ZIP。ZIP 内以该收集目录名称作为唯一顶层目录，包含精简 AEP、复制并重链接的素材和 manifest；manifest 的 `source_file` 必须记录实际 ZIP 文件名。工具必须在报告成功前检查 ZIP CRC，并确认 AEP 与 manifest 均存在；压缩或校验失败时删除该次收集目录和半成品 ZIP，不把不完整产物交给 Eagle。展开目录继续保留用于 AE 打开验收，Eagle 只把同级 ZIP 视为源文件候选。
- 原因：Eagle 的正式入库和 X.bot 源文件发送都以 ZIP 为稳定交付单元。逐合成自动打包能避免人工压缩时把多个包装混在一起或漏掉依赖，同时保留展开目录便于在真实 AE 中复核画面和链接。

## D-028：收集记录与正式入库 manifest 使用不同类型

- 日期：2026-08-20
- 状态：有效
- 决策：逐合成收集器生成的 manifest 使用 `manifest_type: xbot-collection`，只记录合成、对应 ZIP、依赖和收集自检事实；补齐项目、包装、类型、版本、PNG 配对和稳定 ID 的正式入库清单使用 `manifest_type: xbot-eagle-ingest`。Eagle 插件只有在发现正式入库清单时才启用“仅导入 manifest 明确引用文件”；发现收集记录时，读取 `composition.name`、`source_file` 和依赖状态，并按唯一优先级与根目录 PNG 配对。无法唯一配对时必须保持冲突，不允许猜测。旧版未带 `manifest_type` 的收集记录通过 `collector_mode: offline-py-aep` 兼容识别，旧版正式清单继续按 `packages` 或 `package_id` 结构识别。
- 原因：收集记录在生成时尚不知道最终预览 PNG、包装类型和版本，不具备正式入库清单的完整字段。把两者混为一种 manifest 会使插件错误进入全局白名单模式，导致本来有效的 PNG 和 ZIP 全部被忽略；显式类型能保留上游事实，同时把最终配对和人工补充留在 Eagle 入库环节。

## D-029：代表帧默认第 2 秒并允许在外部预览窗口调整

- 日期：2026-08-20
- 状态：有效
- 决策：外部 AEP 收集工具为每个合成默认选择第 2 秒的帧；合成短于 2 秒时回退到最后一个有效帧。用户可在工具预览窗口通过时间轴、秒数输入和前后逐帧重新渲染；只有当前时间已生成真实图像时才能确认。真实画面使用本机已授权 AE 的 `aerender` 后台引擎生成，不打开 AE 主界面；透明通道必须保留。最终 PNG 与 ZIP 同名，`xbot-collection` 写入 `preview_file`、秒数和 AE 帧号，Eagle 优先按显式引用配对。
- 原因：第 0 帧常处于动画尚未进入的空白或初始状态，固定生成一张图又无法应对不同动画节奏。默认第 2 秒能减少大多数手动操作，而可见预览和逐帧调整保留了人工选择代表画面的决定权。离线 AEP 解析不能还原插件、字体、表达式和最终合成画面，因此渲染阶段必须显式依赖 AE 引擎。

## D-030：交互预览使用常驻 AE 加速，视频框从上层包装展示合成取景

- 日期：2026-08-20
- 状态：试行
- 决策：外部 AEP 收集器的交互调帧优先通过可选 `XbotPreviewBridge.jsx` 与已经打开同一 AEP 的常驻 AE 通信，调用 `saveFrameToPng` 快速生成快照；桥接未运行、工程不一致或超时时自动回退 `aerender`，不得自动切换或覆盖用户当前 AE 工程。快速快照只用于选帧，收集阶段始终只额外执行一次高质量 `aerender` 作为最终 PNG。视频框、横屏框和竖屏框默认使用唯一合适的直接父级包装展示合成取景，使框体与背景一起展示；存在歧义时默认自身并让用户明确选择。预览来源只影响 PNG，实际精简 AEP 和 ZIP 仍以用户选中的视频框合成为根，manifest 同时记录两者。
- 原因：FX Console 的速度来自已启动 AE 内的快照工作流，但没有公开自动化接口，不能作为外部工具的稳定依赖。公开 AE 自动化项目证明“常驻面板 + 本地 IPC + `saveFrameToPng`”可以复用 AE 上下文；把快速快照限制在交互阶段，再由现有高质量渲染生成最终图，可以兼顾速度与 Alpha 质量。视频框自身通常只有透明框体，缺少背景和承载画面时不利于 Eagle 中快速辨认，因此需要把展示语境与实际收集边界分开。

## D-031：AE 未打开时优先使用自定义输出模块直接生成 PNG

- 日期：2026-08-20
- 状态：试行
- 决策：后台 `aerender` 预览优先调用名为 `Xbot PNG with Alpha` 的输出模块，直接生成 RGB+Alpha、Straight / Unmatted PNG。程序必须检查 PNG 文件头和 IEND 尾标，只在文件完整后才原子替换目标预览。当前 AE 版本没有该模板、模板名不一致或直接输出失败时，自动回退至已验证的 TIFF+Alpha 中转与反预乘流程。不把 PNG 模板设为收集或渲染的硬前置。
- 原因：`aerender -OMtemplate` 只能按已存在的输出模块名称选择格式，不能只靠 `.png` 扩展名稳定设定格式。自定义英文名称避免了 AE 界面语言造成的内置模板名差异，直接 PNG 又能省去 TIFF 落盘、本地反预乘与再编码环节；保留 TIFF 回退则保证工具在新 AE 版本或其他机器上仍可用。

## D-032：候选操作必须回复机器人消息

- 日期：2026-08-21
- 状态：有效
- 决策：包装候选确认、拒绝、数字选择和类型语境延续都必须回复机器人发出的候选预览或提示消息，并通过飞书 `reply_to` 精确关联查询。没有回复引用时不得查询最近一条 `pending` 记录，不得继承项目，也不得发送源文件；消息继续按新查询或普通聊天处理。多条查询仍可并存，回复任一有效候选消息时仍按其独立状态处理。本决策取代 D-018、D-024 中允许无回复引用回退最近待确认查询的部分，其他规则继续有效。
- 原因：飞书消息可能缺少可用于可靠猜测的上下文，同时会话中可能存在多条历史候选。无引用回退会把新的包装查询、普通领域对话或类型词错误绑定到旧查询，甚至返回过期提示。强制回复把用户操作与查询建立明确关系，能消除歧义并简化状态机。

## D-033：候选内容合并为一条富文本消息

- 日期：2026-08-21
- 状态：有效
- 决策：单候选和多候选统一发送一条飞书富文本消息。消息内按“候选编号与名称 → 对应 PNG”的顺序展示，并在末尾写明回复选择方式、有效期和原查询人限制；不再分别发送图片消息和文字提示。该富文本消息 ID 作为查询的唯一候选交互入口，用户回复它进行确认、拒绝或类型语境延续。
- 原因：图片和文字拆成两条消息会让用户不知道应该回复哪条，也会在群聊插入其他消息后破坏名称与图片的对应关系。统一成一个可回复单元能保持信息完整，并与 D-032 的精确回复规则形成一致的用户心智。

## D-034：接收富文本与纯图片时保持群聊低噪音和图片外发边界

- 日期：2026-09-01
- 状态：有效
- 决策：`lark-cli event consume` 输出的 `post` 富文本先把 `@`、可见文字和图片占位规范化，再进入既有 AI 对话、包装查询和候选确认路由；群聊仍要求有效 `@X.bot`，候选操作仍要求回复引用。纯图片在私聊直接回应；在群聊中仅当事件有效提及 X.bot，或图片消息回复的是 X.bot 消息时回应。当前不下载图片二进制、不发送外部 AI、不基于占位符推断图片内容，只明确说明尚未接入视觉识别并引导用户补充文字。
- 原因：`post` 的可见文字已经由事件消费者转换为可读内容，继续拒绝会中断正常群聊；纯图片没有文字可供当前 DeepSeek 路由理解，若对群内所有图片自动回复会制造噪音，若把图片直接发给外部模型又违反图片外发需明确许可的安全边界。分层处理可以先恢复消息交互，同时保留后续在用户授权后接入视觉能力的路径。

## D-035：重复批次导入必须显式选择处理方式

- 日期：2026-09-02
- 状态：有效
- 决策：Eagle 入库助手检测到相同 `batch_id`、稳定 `batch_key`、源路径或 manifest 标识时，默认暂停导入并要求用户选择“复用现有批次、更新现有批次、新建独立批次”。复用模式不新增已存在的 PNG/ZIP；更新模式复用现有 `package_id` 和 Eagle 素材并刷新批次元数据，缺失的一侧才补导入；新建模式生成独立 `batch_id` 和批次文件夹。批次及包装明细通过 SQLite `batches`/`batch_details` 迁移记录，不能依赖文件夹同名静默判重。
- 原因：同一项目文件夹可能被重复拖入，且同一 `package_id` 的版本或元数据可能发生更新。显式三选项能保留用户对复用、更新和并存版本的决定权，避免重复素材污染 Eagle；SQLite 记录批次身份和明细，为后续插件导入结果与 bot 索引联调提供稳定主键。

## D-036：测试采用精简、精准的最小风险覆盖

- 日期：2026-09-02
- 状态：有效
- 决策：后续测试只为新增行为、关键边界和已知回归风险提供最小有效覆盖。已有实现未发生变化时，不重复增加等价用例；测试数量不作为完成指标。优先选择能直接证明行为的单元或小型集成测试，真实接口验证只在离线测试无法覆盖时加入。
- 原因：项目同时包含 bot、Eagle 插件、SQLite 和 AE 工具链，重复测试会放大维护成本并稀释真正的失败信号。以风险和行为为中心可以保持验证精准，同时让测试集随功能变化而增长，而不是随时间堆积。
